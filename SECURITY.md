# Tenant and AI boundaries

- A browser organization ID is a selector, never authority. Every API operation verifies a Supabase bearer token with the Auth server, then checks membership for that exact organization. Mutation transactions hold a membership lock. Owners publish; staff draft. No public session/AI ingest endpoint exists.
- PostgreSQL RLS limits authenticated reads. Browsers have no insert/update/delete privilege. All mutations are server-controlled. The privileged PostgreSQL connection bypasses RLS, so server queries explicitly scope every tenant-owned access; composite foreign keys prevent cross-tenant record relationships even under privileged access. Organizations/membership provisioning is administrator-only and currently a manual operational step.
- Session IDs and account organizations are immutable in SQL. A trusted transport must provide its own authenticated JID to bind; binding is copied/frozen and re-resolved for each event. Customer identifiers, text and dashboard parameters never choose an inbound tenant. LIDs remain opaque identifiers; no guessed phone mappings.
- Context validation checks account, organization, conversation, contact, revision, memories and history before AI. Delivery re-locks and validates current account, conversation, contact and publication. Human takeover and publication changes suppress pending AI sends. Validation failure emits a content-free security audit event and blocks send.
- Knowledge revisions cannot be edited in place. Publication points to an exact, same-tenant revision. Audit logs preserve drafting/publication actor and resource IDs without raw message content. Uploaded text is not executed, rendered as HTML or promoted to a privileged message. Binary/active document formats are deliberately unsupported.
- DeepSeek can select only a published fact ID. Application code renders the exact approved answer or escalates to a human. No model-authored price, service, policy or appointment confirmation is delivered. Unknown IDs/provider failure return no answer; pricing requests require a pricing-category fact. This intentionally limits natural-language generation and translation. Owner review must ensure approved answers themselves are safe, current and medically appropriate. Prompt safeguards do not replace authorization.
- Prompt size is bounded with lexical knowledge ranking, up to 15 answers, 20 short recent messages and 10 short memories. No vector database or lifetime-history prompt. There are no model tools or SQL execution capabilities.
- Per-conversation queues serialize in-process work; unique database claims prevent multiple workers replying to the same event. External sends and DB commits cannot be atomic: ambiguous sends remain blocked/uncertain for human reconciliation. A crashed processing claim is never automatically retried.

## Release blockers

This implementation has no live WhatsApp adapter, encrypted auth store, media parser, automated memory extraction, spending meter, medical-data classification/redaction, retention scheduler, platform-admin UI or complete appointment workflow. Do not route real patient messages to DeepSeek until privacy configuration and data minimization are implemented and approved. RLS tests use real embedded PostgreSQL, but managed Supabase behavior and the actual service credentials still need staging verification. Review dependency audits and both application and infrastructure configuration before production use.
